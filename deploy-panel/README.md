# GitDeck — отдельная панель обновления из Git

Версия 1.2.3 сохраняет идентификатор и тип редактируемого модуля из его исходной карточки,
даже если автозаполнение браузера изменило заблокированные поля. Папка Git редактируется независимо.
Для Chrono Logos из общего `my_sites` пустая папка в форме заполняется значением `chrono_logos`.

## Chrono Logos — версия 1.2.2

Добавлен отдельный тип модуля **Chrono Logos — игры** для общего репозитория `https://github.com/qboshenkiy/my_sites.git`, папка `chrono_logos`.
Если модуль ранее использовал репозиторий games, в «Настроить» замените ссылку на `https://github.com/qboshenkiy/my_sites.git` и папку на `chrono_logos`, сохранив прежний каталог сервера.
После обновления панели: «Добавить модуль» → выберите этот тип → сохраните готовые параметры → «Обновить из Git».
Первичная установка автоматически создаёт Docker Compose и случайные пароли в пустом `/opt/chrono-logos`, запускает PostgreSQL 17, собирает PHP 8.3 и выполняет миграции.
После установки в «Настройки сайта» задайте `APP_URL=http://IP_СЕРВЕРА:8082/` и свой `ADMIN_PASSWORD` от 12 символов; логин по умолчанию `admin`.

Обновления сохраняют `.env`, сессии и загруженные картинки. Перед обновлением создаётся дамп PostgreSQL; при неудаче возвращаются предыдущий код и полная база. После неудачной первой установки файлы остаются для повторной попытки. Выбор старого коммита не возвращает базу на старую дату. Реквизиты существующей PostgreSQL защищены от изменения через форму, поскольку замена переменных не меняет пароль или имя внутри базы.
DNS и маршрутизация общего HTTPS-прокси настраиваются отдельно. Подробности — `DEPLOY.md` в репозитории games.

Пульс, марафон, сама панель и дополнительные установленные Docker-проекты. Репозитории, ветки, каталоги, параметры запуска и настройки сайтов редактируются в веб-интерфейсе. Можно установить последний commit любой ветки или прошлый commit. История показывает установленный SHA, стадии и журнал. Пароль входа задаётся при установке.

## Управление из интерфейса — версия 1.1.0

- **«Добавить модуль»** подключает проект, уже установленный в отдельном каталоге `/opt/`. Выберите Пульс, марафон или другой Docker-проект. Для стороннего проекта укажите основной сервис, дополнительные сервисы, профили и конкретные папки/файлы с кодом. Dockerfile и compose-файл должны быть уже установлены; панель их не заменяет и не создаёт новый сервер.
- **«Настроить»** меняет название, репозиторий, ветку по умолчанию, папку внутри Git, каталог сервера и Compose-параметры. Идентификатор и тип существующего модуля не меняются; каталог самой панели защищён. Изменения сохраняются без перезапуска GitDeck. Конкурирующее сохранение из другой вкладки отклоняется, чтобы не затереть настройки.
- **«Убрать из панели»** удаляет только подключение. Файлы, контейнеры, базы и история остаются. Идентификатор с историей нельзя повторно использовать для другого проекта.
- **«Ветки и версии»** загружает ветки и 30 последних коммитов выбранной ветки. Выберите commit или введите SHA вручную. В истории есть «Установить версию». Откат к commit меняет код, **не возвращает базу к старой дате**: перед установкой сохраняется её текущее состояние. Совместимость старого кода с текущей схемой базы должна учитываться автором приложения. При ошибке установки автоматически восстанавливается состояние непосредственно перед попыткой.
- **«Настройки сайта» / «Домен и Telegram»** редактирует переменные `.env`: DOMAIN, APP_URL, порт, адрес прослушивания, Telegram-токен, username и дополнительные переменные. Работают только переменные, на которые ссылается существующий compose-файл. COMPOSE_/DOCKER_/GIT_/PYTHON-параметры, PATH и HOME не редактируются через эту форму.
- Секреты не возвращаются браузеру. Пустое поле сохраняет прежний секрет; отдельная галочка очищает его. Чувствительные значения скрываются в журнале применения настроек. Перед изменением сохраняется прежний `.env`, при ошибке запуска возвращается прежний файл. Файлы задания `environment.json` и `previous.env` содержат секреты и хранятся в закрытом каталоге состояния: не публикуйте и не переносите их в Git.
- Применение настроек создаёт отдельное задание и перезапускает выбранные сервисы. Если в этом же Compose есть proxy, он также пересоздаётся с новым окружением. Панель не меняет DNS, внешние настройки провайдера и маршруты общего прокси другого Compose-проекта. Для нового домена настройте A-запись на IP сервера, проверьте DOMAIN и APP_URL. HTTP-compose не становится HTTPS автоматически от изменения DOMAIN.
- Для встроенных Пульса/марафона сохраняется SQLite. У сторонних Docker-модулей резервируется **только код**; их базы, миграции и резервное копирование настраиваются отдельно.

Для получения этих функций в существующей панели нажмите **«Обновить панель»**, после перезапуска войдите снова. Старый self-updater совместим с этим выпуском: HTML и Python остаются в прежних файлах. Конфигурация и пароль сохраняются. При попытке понизить GitDeck проверяется, поддерживает ли выбранная версия текущую конфигурацию модулей.

Linux + systemd, Python 3.10+, Git, Docker Compose V2. Python-пакеты не нужны. Панель слушает **только 127.0.0.1:8120**: домен не нужен, для входа используется SSH-туннель. Она выполняет административные команды от root; не открывайте её порт через прокси или интернет. Репозитории и ветки должны содержать только код, которому вы доверяете.

## 1. Загрузить код в Git

Можно использовать один публичный репозиторий для текущего каталога проекта:

```text
index.php, api.php, assets/, tools/ ...   ← Пульс
marathon/                              ← марафон
deploy-panel/                          ← GitDeck
```

На GitHub создайте пустой публичный репозиторий. Из PowerShell в каталоге проекта:

```powershell
cd C:/laragon/www/my_project
git init -b main
git add .
git status --short
git commit -m "Sites and GitDeck deployment panel"
git remote add origin https://github.com/YOUR_ACCOUNT/YOUR_REPOSITORY.git
git push -u origin main
```

Замените YOUR_ACCOUNT/YOUR_REPOSITORY. Перед commit проверьте staged-файлы: `.env`, базы, реальные токены, ключи и каталоги `dist` не должны попасть в Git. В проектах уже есть правила `.gitignore`. При первом push GitHub потребует вашу авторизацию на ПК.

Если у сайтов отдельные репозитории, используйте разные `repo`. Для репозитория, где код марафона лежит сразу в корне, укажите `subdir: ""`. Для отдельного репозитория панели тоже `subdir: ""`.

## 2. Установить панель на сервер

С ПК загрузите подготовленный архив:

```powershell
scp C:/laragon/www/my_project/deploy-panel/dist/gitdeck.tar.gz root@2.28.57.159:/root/
```

В SSH или консоли Hetzner:

```bash
apt-get update
apt-get install -y python3 git openssh-client
mkdir -p /root/gitdeck-install
tar -xzf /root/gitdeck.tar.gz -C /root/gitdeck-install
bash /root/gitdeck-install/install.sh
```

Задайте отдельный пароль панели, минимум 12 символов. Установщик не меняет сайты или их базы. Если Docker ещё не установлен, сначала установите его и проверьте `docker compose version`.

## 3. Доступ к репозиторию

Для публичных репозиториев оставьте HTTPS-ссылку и `ssh_key: ""` в конфигурации. Токен и deploy key не нужны. **Переходите к шагу 4.**

Следующие действия нужны только если позже решите использовать приватный репозиторий.

Создайте отдельный SSH-ключ на сервере (если этот путь уже занят, выберите другое имя):

```bash
ssh-keygen -t ed25519 -f /root/.ssh/gitdeck -N '' -C gitdeck-readonly
cat /root/.ssh/gitdeck.pub
```

Добавьте **публичный** ключ в GitHub → репозиторий → Settings → Deploy keys → Add deploy key. Доступ на запись не нужен. Для нескольких приватных репозиториев создайте разные deploy keys и укажите соответствующие пути в `ssh_key` каждого проекта. Закрытый ключ не копируйте в репозиторий или чат.

Один раз подключитесь к GitHub, чтобы проверить и сохранить ключ хоста:

```bash
ssh -i /root/.ssh/gitdeck -o IdentitiesOnly=yes -T git@github.com
```

Проверьте показанный fingerprint по официальной документации вашего Git-сервиса, затем подтвердите. Успешный GitHub-ответ сообщает об аутентификации и отсутствии shell-доступа; ненулевой код выхода у этой проверки нормален. Панель требует уже проверенный known_hosts и сама не принимает неизвестные ключи.

Публичный HTTPS-репозиторий работает без `ssh_key` — удалите поле или оставьте пустую строку. Не вставляйте токены или пароль в URL.

## 4. Указать существующие установки

```bash
nano /etc/gitdeck/config.json
```

В каждой карточке замените `repo` и проверьте:

- `directory`: реальный каталог сайта. Для марафона `/opt/marathon`. Для Пульса проверьте, где лежит его compose-файл — пример `/opt/pulse` нужно заменить, если путь другой.
- `compose`: тот файл, которым сайт запущен сейчас: `compose.yaml`, `compose.https.yaml` или `compose.shared.yaml`.
- `profiles`: `["telegram"]` для работающего бота, иначе `[]`.
- `services`: `["web", "bot"]` с ботом, иначе `["web"]`.
- `branch`: ветка для установки, обычно `main`.
- `subdir`: путь к коду внутри Git, не путь на сервере.
- у самой панели `kind: "self"`, `directory: "/opt/gitdeck"`.

Не меняйте compose project name, тома или рабочие `.env`: панель использует существующие настройки. Сначала сайты должны быть установлены и база создана. Поиск установки с сервера: `docker compose ls`.

```bash
systemctl restart gitdeck
systemctl status gitdeck --no-pager
```

## 5. Открыть панель с компьютера

В **PowerShell на вашем ПК**, а не в консоли сайта Hetzner:

```powershell
ssh -L 8120:127.0.0.1:8120 root@2.28.57.159
```

Не закрывая это окно, откройте **http://localhost:8120** в браузере и введите пароль GitDeck. Локальный и серверный порт должны быть 8120: это также защищает от постороннего Host/Origin. При смене порта измените его и в config.json, и в обеих частях туннеля.

## Как выпускать обновления

1. Доработайте код на ПК и проверьте локальные сайты.
2. Выполните `git add .`, `git commit -m "Описание изменений"`, `git push`.
3. Откройте GitDeck → нужный проект → «Обновить из Git» → подтвердите установку.
4. Дождитесь «Установлено» и проверьте сайт. Во время сборки он временно недоступен.

Панель получает ветку, фиксирует SHA, извлекает только разрешённый код без исполнения Git-хуков, проверяет обязательные файлы. Для сайта останавливает web/бота, делает консистентный SQLite backup и заменяет код. Сайт запускает через `docker compose up --build --wait web`, затем отдельно запускает бота без `--wait` и проверяет, что его процесс остаётся запущенным. У бота отключён healthcheck; эта проверка не подтверждает подключение к Telegram. Caddy/proxy не перезапускается. Одновременно выполняется только одно обновление.

При ошибке после замены кода выполняется восстановление прежнего кода и базы. Записи, сделанные после запуска неудачной версии до её отката, могут быть потеряны. При ошибке самого восстановления журнал содержит обе ошибки; резервные копии остаются на диске. Задание не признаётся успешным до прохождения запуска.

Для самообновления создаётся отдельное systemd-задание с копией текущего worker. Оно обновляет `/opt/gitdeck` и перезапускает `gitdeck.service`, проверяет HTTP `/health`; при ошибке возвращает прежние файлы. Пароль, история, репозитории и конфигурация остаются в `/var/lib/gitdeck` и `/etc/gitdeck`. После успешного перезапуска войдите снова.

### Что обновляется

Пульс: PHP-код, `.htaccess`, `assets/`, два PHP-инструмента. Марафон: PHP-код, `.htaccess`, `assets/`, `lib/`, бот и backup-инструмент. Панель: собственный Python/HTML и документация.

**`.env`, storage, Dockerfile, compose-файлы, Caddy, тома и конфигурация GitDeck не заменяются.** Изменения инфраструктуры применяются отдельно после проверки. Такой подход сохраняет текущие домены и настройки на вашем сервере; если будущему релизу понадобятся новые системные зависимости, одного обновления кода будет недостаточно.

## Обслуживание и восстановление

```bash
journalctl -u gitdeck -n 50 --no-pager
ls /var/lib/gitdeck/jobs
cat /var/lib/gitdeck/jobs/JOB_ID/output.log
```

В каждом задании: `previous/` — прежний код, `new/` — загруженная версия, `data.sqlite` — база до изменения (для сайта), `previous-version.json` — прежний SHA. Резервные копии не удаляются автоматически: периодически переносите нужные копии и очищайте старые завершённые задания, контролируя свободное место.

После перезагрузки сервера или принудительного завершения worker обновление может остаться незавершённым. Проверьте журнал и сервисы; для снятия блокировки **только после остановки задания**:

```bash
python3 /opt/gitdeck/app.py --config /etc/gitdeck/config.json recover
```

Команда не восстанавливает данные и не объявляет установку успешной. Если автоматический откат не удался, остановите web/бота, верните управляемые файлы из `previous/` и восстановите `data.sqlite` по инструкции резервного копирования проекта. Не удаляйте Docker-тома.

Смена пароля: `python3 /opt/gitdeck/app.py password`, затем `systemctl restart gitdeck` для закрытия старых сессий.

## Проверка разработки

```bash
python3 tests.py
```

Тесты используют временные Git-репозитории и имитацию Docker/systemd, проверяют установку и восстановление кода/базы, защиту путей, allowlist, пароль, сессии и CSRF. Дополнительно `check_docker.py` проверяет реальное резервное копирование и восстановление SQLite в одноразовых Docker-контейнерах обоих сайтов, если локальные образы уже собраны. Этот тест прошёл в среде разработки. Полный цикл Linux/systemd, включая самообновление сервиса, проверяется после установки; на сервер пользователя из среды разработки подключение не выполняется.
# HTTPS Chrono Logos на существующем домене — 1.3.0

В настройках Chrono Logos можно выбрать работающий HTTPS-прокси марафона/Пульса
и подготовить адрес `https://vano.sbena.net:8083/` без покупки другого домена.
Нужны Compose 2.24+ и основной блок `{$DOMAIN}` в существующем `deploy/Caddyfile`.
Панель сохраняет маршруты прокси, создаёт дополнительные Compose-файлы,
проверяет Caddyfile и при ошибке возвращает изменённые файлы.
Входящий TCP 8083 разрешается в Hetzner отдельно. При применении Caddy кратковременно пересоздаётся.

Токен отдельного бота и его имя задаются в настройках Chrono Logos; после применения
администратор подключает бота кнопкой в профиле самого сайта.
Полные шаги: [Chrono Logos DEPLOY.md](../chrono_logos/DEPLOY.md).

## HTTPS на поддомене — 1.3.1

Для Chrono Logos теперь можно задать `APP_URL=https://chrono.vano.sbena.net/`
и выбрать общий HTTPS-прокси в настройках сайта. DNS поддомена должен указывать
на сервер. Игра использует существующие порты 80/443; порт 8083 открывать не нужно.
Основной сайт марафона сохраняет свой адрес. В журнале применения отображается
исходная причина ошибки с маскировкой секретов; при отказе предварительной проверки
контейнеры не перезапускаются. Прежний вариант HTTPS на отдельном порту поддерживается.

## Штрих — 1.4.0

Новый тип модуля «Штрих — рисунки и ИИ» устанавливает отдельный сайт из папки `sketch_game`
в пустой каталог, создаёт Compose и постоянный SQLite-том. Поддержаны HTTPS через общий
прокси, настройки ключа ИИ и кода участников, резервное копирование и возврат базы при сбое.

## Восстановление маршрутов HTTPS — 1.4.1

Если главный домен марафона стал показывать Chrono Logos, обновите панель и нажмите
**Восстановить HTTPS** в карточке Chrono Logos. Открывать или менять настройки не нужно.
Панель назначит основному сайту отдельное Docker DNS-имя, пересоздаст web с этим именем
и перезагрузит прокси. Это устраняет коллизию общего имени `web` в сети двух проектов.
Адрес игры и остальные переменные сохраняются; при ошибке прежние файлы возвращаются.
