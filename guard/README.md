# Guard

Отдельный центр защиты и управления собственными Telegram-ботами: https://guard.vano.sbena.net.

- Вход администратора, scrypt-пароль, HttpOnly/SameSite/Secure cookie на HTTPS, CSRF, ограничение попыток входа.
- Успешные и неудачные SSH-входы: IP, пользователь, способ и время.
- HTTP: запросы, ошибки 4xx/5xx, IP, пик запросов за минуту, последние обращения. Источник — журнал доступа Caddy; до 10 000 последних строк за час или сутки. Это выборка, а не биллинг всего трафика.
- Marathon и Pulse: состояние и запуск/остановка/перезапуск бота. Milk работает внутри сайта, поэтому управление его контейнером остаётся в GitDeck.
- Участники из существующих Telegram-привязок и новые собеседники, личные диалоги, поиск, индивидуальный ответ. Для старых привязок без новых сообщений время последнего обращения неизвестно. Блокировка запрещает обработку входящих сообщений и команд от Telegram ID; она не удаляет аккаунт, результаты и не отключает плановые уведомления.
- Диалоги сохраняются с момента установки обновлённого бота, до 30 дней / 50 000 сообщений на бот. Коды входа, длинные токены, URL скрываются. Telegram не предоставляет историческую переписку через Bot API. Сообщения групп в личный журнал не копируются.
- Аудит входов в Guard и действий администратора хранится 90 дней. Пароль, cookies, токены ботов и тела HTTP-запросов в интерфейс не передаются.

## IP: история, карта и меры

В разделе «Защита IP» и по кнопке IP в журналах/предупреждениях доступны:

- полные пути запросов с безопасным редактированием токенов, методы, домены, время, коды, размеры ответов, длительность, протокол, User-Agent;
- статистика за час, сутки или неделю и скользящий максимум запросов за 60 секунд;
- признаки сканирования служебных файлов, отдельные журналы SSH и входов в Guard, экспорт JSON;
- примерная страна, город, ASN/провайдер и карта OpenStreetMap. Это расположение сети/VPN/дата-центра, а не человека. География запрашивается у IPinfo по выбору IP и кешируется на сутки; Google Cloud сверяется с опубликованными диапазонами, если применимо;
- блокировка одного IPv4/IPv6 на 15 минут, час или сутки и досрочное снятие.

Блокировка действует на **все входящие порты сервера**, а не только Caddy: HTTP/HTTPS, SSH, UDP и опубликованные порты Docker. Отдельная служба `guard-firewall.service` управляет только своей таблицей `inet guard_protection`. Входной и транзитный трафик проверяются до разрешающих правил Docker; существующие Docker/Fail2ban таблицы не изменяются. Сроки действуют в ядре nftables, даже при остановленном Guard. Состояние сохраняется для перезагрузки. Текущий IP администратора, адреса сервера и служебные диапазоны защищены от случайной блокировки; лимит — 256 активных адресов.

Контроллер принимает только status/block/unblock по локальному Unix socket с правами root 0600. Установку выполняет `python3 src/install_firewall.py` на хосте; `setup.py` вызывает её автоматически. Для существующего развёртывания создаётся overlay `compose.gitdeck-guard.yaml` с сокетом. После установки нужен обычный перезапуск/обновление Guard через GitDeck. Служба имеет только CAP_NET_ADMIN, её файловая система ограничена каталогами состояния.

`proxy_protection.py` закрывает на уровне Caddy `.env`, `.git`, `.svn`, `.aws`, `.ssh`, `phpinfo.php` и сохраняет все текущие маршруты. Кандидат конфигурации проверяется до применения, сохраняется резервная копия. Блокируются только служебные пути; обычные API и загрузки продолжают работать.

HTTP-метаданные сохраняются в SQLite 7 дней, максимум 200 000 записей на сервер; в карточке до 500 последних строк. Это доступная выборка журналов, а не доказательство полного отсутствия компрометации. Cookies, Authorization, тела POST и секретные значения query не сохраняются. После полной блокировки запросы не доходят до приложения/SSH, поэтому их URL и содержимое входа не появляются в этих журналах. Счётчик отброшенных пакетов доступен в защите.

Для аварийного восстановления только этих правил через консоль провайдера: остановить `guard-firewall.service`, затем удалить таблицу `inet guard_protection`. Это не меняет остальные таблицы Docker/Fail2ban.

## Уведомления

Раздел «Уведомления» работает в фоне, даже когда сайт закрыт. По умолчанию предупреждает о 240 HTTP-запросах за скользящие 60 секунд с одного IP к одному сайту, 60 входящих сообщениях одному боту от одного Telegram ID, каждом HTTP 500–599 и сбоях обработки/отправки ответа ботами. Пороги настраиваются. Повторные события объединяются на 10 минут. Высокая частота сама по себе не доказывает атаку: автоматической блокировки нет.

Отправка в Telegram выполняется только отдельным ботом:

1. Создайте нового бота через BotFather и новую группу.
2. В «Уведомлениях» вставьте токен, включите отправку в Telegram и сохраните настройки. Токен не возвращается через API и не попадает в журнал действий.
3. Добавьте бота в группу администратором. Нажмите «Получить команду подключения».
4. Администратор группы отправляет полученную команду `/guard@имя_бота код` в группу. Код одноразовый и действует 15 минут.
5. Обновите страницу Guard и нажмите «Отправить проверку в группу».

В уведомлении указаны сайт/бот, IP либо Telegram ID, код ошибки и количество событий. Тексты личных сообщений и параметры URL в группу не отправляются. Старые предупреждения в новую группу не пересылаются. Сводка содержит до 5 предупреждений и отправляется не чаще раза в 30 секунд; при сетевой ошибке и Telegram 429 сохраняется очередь с повторной попыткой. Одно событие может повторно доставиться при неоднозначном сетевом таймауте после принятия сообщения Telegram.

Предупреждения хранятся в SQLite до 30 дней, максимум 5000. Сохраняются курсоры активности и дедупликация после перезапуска. Проверка выполняется примерно раз в 30 секунд, HTTP — по доступной выборке последних 3 минут (обычно до 2000 строк, сокращается при чрезмерном объёме). Для ботов используются новые события локального журнала; повторная обработка одного Telegram update не считается новым спам-сообщением. Фоновый сервис показывает время проверки, очередь и ошибки сбора/доставки в интерфейсе.

## Развёртывание

`python3 src/setup.py` запускается на сервере с установленным GitDeck. Создаёт том Guard, копирует существующий хеш пароля GitDeck для первоначального входа, добавляет маршрут HTTPS, доступ к журналам Caddy и карточку в GitDeck. Повторный запуск сохраняет пароль и данные. Порт 8150 привязан только к localhost; Caddy подключается по внутренней Docker-сети.

Для отдельного пароля: `docker compose exec web python src/app.py password`. Обновление кода выполняется через карточку Guard в GitDeck; данные и конфигурация Docker сохраняются.

Guard имеет доступ к Docker socket для управления строго заданными ботами, а также к журналу SSH хоста. Это привилегированная административная панель. Не используйте её как публичный сайт без входа. Сессии истекают через 8 часов; после смены пароля все сессии отзываются.

## Проверка

`python3 -m unittest discover -s guard/tests` и `node guard/tests/navigation.cjs`

PHP-хук одинаков в `marathon/lib/bot-guard.php` и `assets/bot-guard.php`. Python-хук Milk находится в `milk_duty/src/bot_guard.py`. Токены остаются внутри соответствующего контейнера; Guard не опрашивает getUpdates ботов приложений. Для собственного отдельного бота уведомлений используется независимый poller; токен действующего бота приложения отклоняется при настройке.


HTTP-защита на всех доменах использует общую скользящую очередь: 30 запросов
с IP за 10 секунд. 31-й запрос получает 429 и вызывает блокировку всех портов
на 300 секунд через host nftables; пять разных служебных путей за минуту
также вызывают такую блокировку. Адреса из `/etc/guard-firewall.json` получают
429 без блокировки администраторского доступа. Внутренние проверки здоровья
не учитываются. IP берётся из соединения Caddy, клиентские заголовки его не
подменяют. `guard-request-gate.service` доступен только через Unix-сокет
в существующем `/data` Caddy, внешнего порта нет. Установка выполняется
`python3 /opt/guard/src/proxy_protection.py` после установки firewall.
При недоступности проверяющего сервиса Caddy прекращает передачу запросов
приложениям; systemd автоматически перезапускает сервис. Для диагностики:
`journalctl -u guard-request-gate.service`.

Отдельная вкладка «Журнал SSH» показывает подтверждённые успешные входы,
неудачные попытки, пользователя, IP, порт клиента и способ авторизации.
Доступен поиск по IP/пользователю и фильтр результата. Это события sshd,
не список всех TCP-пакетов; сетевые блокировки до sshd в журнал не попадают.
